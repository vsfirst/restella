**E2E가 확인한 것 ("마지막 1실" 시연 시나리오)**
- 로그인하지 않으면 로그인 화면으로 이동하고, 틀린 비밀번호는 거절된다 (AC-18-1)
- 로그인 토큰이 `document.cookie`와 HTML에 없다 (AC-18-3)
- 남은 1실에 50건: 결과 화면에 "50건 중 1건만 확정", "초과 판매 0건" (AC-19-2, AC-19-3)
- 새로고침 없이 5초 안에 충돌 알림과 배지가 나타난다 (AC-13-2)
- 해결됨은 메모 없이는 누를 수 없고, 처리하면 미처리 목록에서 빠진다. 취소도 같다 (AC-14-1·2·3)
- 재고 달력에서 해당 날짜가 매진이다 (AC-02-2)
- 5개 채널 모두 5초 안에 "0 · 판매 중지"를 받았다 (AC-20-1)
- 이벤트 로그에 충돌과 처리 기록이 있다 (AC-17-1)
- 예약 상세에 차감된 숙박일이 보인다. 로그아웃하면 다시 로그인해야 한다 (AC-18-2)

**서버 렌더링 확인:** 로그인한 쿠키로 `/inventory`의 HTML을 받아, 재고 칸 42개(객실타입 3 × 14일)가 처음 응답에 들어 있고 토큰 문자열은 없음을 확인했다.

## front-end에서 발견하고 고친 문제

| # | 발견 | 원인 | 조치 |
|---|---|---|---|
| F1 | 모든 화면에서 "prerendering 중 `Date.now()`" 오류 로그 | Partial Prefetching이 쿠키가 있는 요청의 앱 셸을 미리 렌더링하는데, iron-session이 쿠키를 풀며 현재 시각으로 만료를 확인함 | 세션을 읽기 전에 `connection()`을 불러 요청 시점에만 읽음. 오늘 날짜를 쓰는 화면도 같음 |
| F2 | E2E 첫 로그인 테스트 실패 (오류 메시지가 안 보임) | React가 화면을 붙이기 전에 버튼이 눌리면 폼이 브라우저 기본 동작(GET)으로 제출됨. **비밀번호가 URL 쿼리에 실릴 수 있는 문제** | 폼을 `method="post" action="/api/auth/login"`으로 바꾸고 BFF가 폼 제출도 받아 303으로 이동. 이동 경로는 같은 사이트만 허용 |
| F3 | E2E 재실행 시 로그인 실패(429) | back-end 로그인 제한이 IP 기준인데, BFF를 거치면 모든 운영자가 front-end 서버 IP 하나를 씀 | 데모(운영자 1명)에서는 유지하고 알려진 제약으로 기록([front-end 설계](../../front-end/README.md#인증-흐름)) |
| F4 | 채널별 재고 스크린샷이 로딩 화면으로 찍힘 | 스트리밍된 내용은 화면에 드러나기 전(React가 최대 약 0.3초 늦춰 드러냄)에도 DOM에 있어 개수 검사를 통과함 | E2E가 화면에 보이는 요소만 세도록 고침 |
| F5 | 서버 컴포넌트에서 쓰는 상수를 `'use client'` 파일에서 export | 서버에서 클라이언트 파일의 export는 값이 아니라 참조로 바뀜 | 상수를 별도 파일로 분리 (빌드 전에 코드 검토로 발견) |
| F6 | 컨테이너에서 E2E 로그인 실패 테스트가 다른 앱의 404 화면을 받음 | 로그인 폼이 기본 동작으로 제출되면 BFF가 `request.url`로 이동 주소를 만들었는데, 컨테이너 안에서는 서버 바인드 주소 `0.0.0.0:3000`이 됨. 이 컴퓨터에서는 3000번을 쓰는 다른 앱(Open WebUI)으로 감 | BFF의 303은 상대 경로 `Location`으로, `proxy.ts`는 요청의 Host로 주소를 만드는 `nextUrl`로 바꿈. 다른 Host로 요청해도 올바른 경로로 가는 것 확인 |

## 테스트로 발견하고 고친 문제 (back-end)

| # | 발견 | 원인 | 조치 |
|---|---|---|---|
| 1 | 첫 E2E 실행에서 대부분 500 | TypeORM 1.x의 INSERT 결과 형식과 맞지 않는 방식으로 새 ID를 꺼내 `NaN`이 됨 | TypeORM이 채우는 `identifiers`로 ID를 꺼냄 |
| 2 | 같은 실행에서 교착 18건 | 같은 키를 먼저 INSERT한 트랜잭션이 롤백되면 그 키를 기다리던 트랜잭션들끼리 교착에 빠지는 InnoDB의 알려진 동작. 1번 오류로 롤백이 일어나 드러남 | 1번을 고친 뒤 동시성 테스트 5회 반복에서 교착 0건 확인. 같은 상황이 운영에서도 생길 수 있어 교착·잠금 대기 시간 초과 시 트랜잭션을 최대 3회 다시 시도(`withLockRetry`) |
| 3 | 동기화 테스트 실패 | 테스트마다 DB를 비워 revision이 1부터 다시 시작했는데, 가짜 채널은 이전 테스트의 높은 revision을 기억하고 새 값을 "오래된 값"으로 무시함 (운영에서는 revision이 줄지 않음) | 테스트 초기화에 가짜 채널 상태 초기화 추가(운영자 API로도 제공) |
| 4 | 앱 종료 시 "Pool is closed" 로그 | 진행 중인 동기화 전송이 끝나기 전에 DB 연결이 닫힘 (Pod 재시작 때도 발생 가능) | 종료 전에 진행 중인 전송을 기다림 (`beforeApplicationShutdown`) |
| 5 | REQ-20 테스트 간헐 실패 | 가짜 채널이 값을 받은 직후, 발송기가 "보냄"을 기록하기 전에 조회함 (테스트의 경쟁 조건) | API가 동기화 완료 상태가 될 때까지 기다리도록 테스트를 고침 |
| 6 | 빌드 결과물의 Swagger 문서에 요청 형식이 비어 있음 | Swagger 플러그인은 기본적으로 `*.dto.ts`만 분석하는데 DTO가 컨트롤러 파일에 있음 | 플러그인 분석 대상에 컨트롤러 파일 추가. 이후 DTO를 `dto/*.dto.ts`로 분리하면서 기본 설정으로 되돌림(2026-10-10) |

## infra (2026-10-11)

- **로컬 k3s:** demo와 같은 k3s v1.36.5를 Docker에 띄워 차트를 배포하고, 배포된 front-end 차트를 대상으로 Playwright E2E 2개가 통과했다. 세부 내용은 [infra 설계](../../infra/README.md)의 차트별 "검증"에 있다.
- **demo 배포:** t4g.large 스팟 노드 1대(k3s v1.36.5, Argo CD 3.5.4, ESO 2.12.0, cert-manager v1.21.2, Traefik 3.7.13). Application 8개 모두 Synced/Healthy, mariadb·back-end·front-end Pod 실행, 마이그레이션·시드 Job 완료.
- **HTTPS:** `fe.`·`api.` 도메인에 Let's Encrypt 인증서가 발급됐고, HTTP 요청은 301로 HTTPS에 넘어간다(AC-N03-2).
- **모니터링:** `grafana.` 도메인에 Let's Encrypt 인증서가 발급됐다. 로그인 없이 Restella 대시보드를 조회할 수 있고, 익명 편집 시도는 403이다. Prometheus가 back-end `/metrics`를 수집한다(`up=1`, 예약 결과 지표 확인, AC-N05-1).
- **CI:** `demo-back-end`·`demo-front-end` 워크플로가 테스트 → arm64 빌드 → ECR 푸시 → 이미지 다이제스트 커밋까지 성공했다(AC-N06-1). 공개된 Actions 로그에 AWS 계정 ID가 그대로 찍힌 줄은 없다.
