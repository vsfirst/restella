# 범위

> 초안. P0에서 사람이 확정한다. "여유가 되면"의 진행 상태는 2026-10-11 기준이다.

요구사항 단위의 상세 내용과 완료 조건은 [요구사항](requirements.md)에 있다. 아래 "포함"은 Must, "여유가 되면"은 Should·Could 요구사항에 해당한다.

## 포함 (MVP)

- **재고 원장:** 객실타입 × 숙박일(박) 단위로 관리한다. 체크아웃 날짜는 차감하지 않는다.
- **예약 수신 API:**
  - 연박은 모든 날짜를 한꺼번에 잡거나 하나도 잡지 않는다.
  - 동시 요청에 안전하고, 같은 웹훅이 다시 와도 한 번만 처리한다.
  - 확인형 채널은 매진이면 거절한다.
  - 통보형 채널은 매진이면 '오버부킹 충돌'로 기록한다.
- **취소와 동기화:** 취소하면 재고를 되돌리고, 재고가 바뀌면 모든 채널에 남은 수량을 동기화한다. 채널은 시뮬레이터로 대체한다.
- **운영자 콘솔:** 로그인, 재고 달력, 예약 목록, 충돌 처리함, 이벤트 로그.
- **동시 예약 시뮬레이터:** 남은 1실에 여러 채널이 동시에 요청했을 때의 결과를 화면에서 확인한다.

## 제외

| 항목 | 이유 |
|---|---|
| 실제 OTA API 연동 | 파트너 계약이 필요하다. 채널 연결부는 인터페이스로 만들고 시뮬레이터로 대체한다 |
| 결제, 요금·프로모션, 회원, 개별 객실 배정, 여러 숙소 지원 | 이번 문제 해결과 관계가 없다 |
| Redis 분산 락, 메시지 큐 | DB 트랜잭션으로 충분하다. 근거는 ADR로 남긴다 |
| 고가용성(멀티 노드, 관리형 DB) | 과제 규모에 맞춰 EC2 1대로 구성한다. 데이터는 EBS 스냅샷으로 보호한다 |

## 여유가 되면

| 항목 | 상태 |
|---|---|
| 총 재고 조정 (REQ-03, Should) | 구현 |
| 채널 동기화 실패 재시도 (REQ-12, Should) | 구현 |
| 충돌 예약을 다른 객실타입으로 옮기기 (REQ-15, Could) | 구현 |
| 채널별로 받은 재고 보기 (REQ-20, Should) | 구현 |
| Transactional Outbox로 동기화 신뢰성 보장 | 다른 방식으로 구현. 이벤트 Outbox 대신, 재고 변경과 같은 트랜잭션에 채널별 동기화 상태를 기록한다. 누락이 없다는 보장은 같다([ADR-0004](../adr/0004-reservation-consistency-and-sync.md)) |
| 수동 마감과 즉시 동기화의 오버부킹 비교 시뮬레이션 | 하지 않음 |
| 부하 테스트 | 남음. demo 환경에서 p95를 측정한다(AC-N02-1) |

진행 상태는 [요구사항 추적표](../4-testing/traceability.md)에서 확인할 수 있다.
