# ADR-0004: 예약 정합성과 채널 동기화 방식

- 상태: 채택
- 날짜: 2026-10-09

## 맥락

- 남은 1실에 여러 채널의 요청이 동시에 몰려도 초과 판매가 없어야 한다(REQ-05, NFR-01).
- 연박은 모든 숙박일을 한꺼번에 잡아야 한다(REQ-04).
- 채널은 같은 예약을 다시 보낼 수 있다(REQ-08).
- 재고가 바뀌면 모든 채널에 5초 안에 알려야 하고, 실패하면 다시 보내야 한다. 이때 늦게 도착한 오래된 값이 최신 값을 덮으면 안 된다(REQ-11, 12).
- 운영 환경은 EC2 1대, MariaDB 1대다([ADR-0001](0001-network-topology.md)).

## 결정 1: 동시성 제어는 DB 비관적 잠금

| 후보 | 판단 |
|---|---|
| **재고 행을 날짜 순서로 `SELECT … FOR UPDATE`** | **채택.** 경합이 심한 "마지막 1실"에서도 대기 후 순서대로 처리되어 재시도가 없다. 잠금 순서를 고정하면 교착도 없다 |
| 낙관적 잠금(버전 컬럼 + 재시도) | 경합이 심하면 대부분이 실패하고 재시도가 폭증한다. 50건 동시 요청에서 49건이 재시도 경쟁을 한다 |
| 조건부 UPDATE 한 문장(`WHERE sold < total`) | 연박에서 행 잠금 순서가 실행 계획에 따라 달라질 수 있어 교착 위험이 남는다 |
| Redis 분산 락 | DB가 1대인데 잠금 서버를 따로 둘 이유가 없다. 인프라와 장애 지점만 는다 |
| 메시지 큐로 요청 직렬화 | 응답이 비동기가 된다. 확인형 채널은 즉시 확정 또는 거절을 받아야 해서 맞지 않는다 |

마지막 방어선으로 `CHECK (sold_rooms <= total_rooms)`를 둔다. 로직이 틀려도 초과 판매는 저장되지 않는다.

## 결정 2: 중복 요청은 DB 유일키로 판별

- `UNIQUE(channel_id, channel_reservation_no)`를 건다. 예약을 처리하는 트랜잭션의 첫 단계에서 예약 행을 INSERT한다.
- 별도의 멱등 키 테이블이나 캐시를 두지 않는다. 동시에 같은 요청이 와도 InnoDB 유일키가 하나만 통과시킨다.
- 거절된 예약도 저장한다. 그래야 같은 요청이 다시 와도 같은 결과를 돌려줄 수 있다.
- 같은 번호로 내용이 다른 요청이 오면 `request_hash`로 감지해 오류로 응답한다. 예약 변경은 범위 밖이다.

## 결정 3: 채널 동기화는 "보내야 할 상태" 테이블

| 후보 | 판단 |
|---|---|
| 커밋 후 메모리에서 바로 전송 | 서버가 커밋 직후 죽으면 동기화가 사라진다. 재시도 상태도 남지 않는다 |
| 이벤트 Outbox(변경마다 이벤트 행 추가) | 누락은 없다. 하지만 같은 숙박일의 이벤트가 쌓이면 순서와 중복 처리가 필요하고, 재시도 중 최신 값 보장이 복잡하다 |
| **상태 테이블(`channel_availability`)에 desired/sent 기록** | **채택.** 재고를 바꾸는 트랜잭션 안에서 "채널마다 보내야 할 최신 값"을 덮어쓴다. 발송기는 `desired_revision > sent_revision`인 행만 보낸다 |

채택한 방식의 효과는 다음과 같다.
- **누락 없음:** 재고 변경과 동기화 기록이 함께 커밋된다(Outbox와 같은 보장).
- **최신 값만 전송:** 같은 숙박일이 여러 번 바뀌어도 행은 하나이고 항상 최신 값을 담는다. 채널에는 `revision`을 함께 보내서 늦게 도착한 값을 무시하게 한다.
- **화면과 지표에 그대로 활용:** `sent_*`는 "채널별 재고 보기"(REQ-20)의 데이터가 되고, `sent_at - changed_at`은 동기화 지연 지표가 된다.

발송기는 back-end 안에서 동작한다.
- 1초마다 대상 행을 고른다.
- 예약을 처리한 직후에는 바로 깨워서 지연을 줄인다.
- 실패하면 간격을 늘려 최대 5회 다시 시도한다.
- 노드가 1대이므로 발송기도 하나만 돈다. 노드가 여러 대가 되면 `SELECT … FOR UPDATE SKIP LOCKED`로 행을 나눠 가지도록 바꾼다.

## 결정 4: 충돌 실시간 알림은 SSE

| 후보 | 판단 |
|---|---|
| **SSE (back-end `@Sse` → Next.js BFF가 스트림 중계)** | **채택.** 서버에서 브라우저로 한 방향 알림만 있으면 된다. NestJS 기본 기능이라 추가 패키지가 없다 |
| 폴링(TanStack Query 3초 간격) | 5초 조건은 만족하지만 계속 요청을 보낸다. SSE가 끊겼을 때를 위한 보조 수단으로 남긴다(10초 간격) |
| WebSocket | 양방향이 필요 없다. 구성 요소만 는다 |

front-end는 SSE 이벤트를 받으면 해당 TanStack Query 캐시를 무효화해서 다시 조회한다. 이벤트 자체에 데이터를 싣지 않고 "무엇이 바뀌었다"만 알린다. 권한 검사와 데이터 형식이 기존 조회 API 한 곳에만 있게 하려는 것이다.

## 결과

- 모든 쓰기 트랜잭션은 `READ COMMITTED` 격리 수준을 쓴다. MariaDB 기본값의 간격 잠금으로 생기는 불필요한 대기와 교착을 피한다.
- 테스트는 Testcontainers로 실제 MariaDB를 띄워서 한다. 잠금 동작은 DB마다 달라서 모의 객체(mock)로는 검증할 수 없다.
- 노드가 1대라는 전제(발송기 1개, SSE 연결 관리)는 prod에서 노드를 늘릴 때 다시 검토한다.
